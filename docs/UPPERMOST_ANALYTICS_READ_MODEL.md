# Analytics and communication read models

`orders`, payment attempts, subscription state and shipments remain authoritative. Raw `analytics_events` remains historical browser telemetry. Communication rules read `communication_customer_features`; they never repeatedly join or aggregate those historical tables.

Confirmed-order events increment order count/spend/product aggregates once using `communication_projection_receipts`. Subscription changes maintain a small per-subscription projection, from which a single customer's active counts and dates are updated. Payment/shipment timestamps reject older facts. Browser ingest maintains one compact visitor behavior row and projects identified product/cart/last-seen state. Purchase state from confirmed commerce events suppresses abandoned-cart messaging even before an older browser event catches up.

Indexes match due rules/outbox, run recipients, feature last-order/charge/cart timestamps, customer preference keys and identity current/customer lookup. Scheduled work uses customer UUID keysets with a 500-row cap; events add a single customer constraint. OR expressions cannot escape either constraint. Preview caps at 100 without a wide exact count.

Recovery is explicitly manual and bounded; it does not run historical commerce scans on each rule tick. `RECOVER_STATE` scans at most 100 primary-key rows from a whitelisted orders/subscriptions/payments/shipments source per invocation and stores a durable cursor. Payment/shipment batches resolve only their 100 owned order references. Events deduplicate against normal capture keys and carry `projection_only`, so historical backfill does not launch campaigns. Repeat each source until the returned count is below 100. Corrections/refunds and lost original message intents still need explicit reconciliation before historical segmentation is treated as complete. Do not reset feature totals and replay receipts without a coordinated rebuild.

The disposable PGlite test applies all migrations and creates 500,000 synthetic customers/features. It checks 500-row pages, deterministic subsequent cursors and an indexed last-order/keyset plan. [Saved EXPLAIN ANALYZE](communication-query-plan.json) shows local WASM Postgres behavior, not production latency or a Supabase load test. Run representative plans in staging with actual statistics/distribution, inspect rows removed by filters, and assess selective predicates, timeout behavior and provider/backlog throughput. A derived model protects hot tables but can still need additional targeted indexes at scale.

Monitor projection receipt lag versus pending outbox age, feature updated_at, query_duration_ms, batch_count and PAUSED_PERFORMANCE_GUARD. Frequency counters are cached observations; actual caps use recent indexed reservations. Product-affinity/friction fields are reserved for internal intelligence and must not generate behavioral complaints to customers.
