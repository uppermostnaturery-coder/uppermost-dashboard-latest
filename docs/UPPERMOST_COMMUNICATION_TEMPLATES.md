# Canonical templates and provider lifecycle

Existing `message_templates`, `customer_messages` and `message_deliveries` remain compatible. `communication_templates` owns a logical key; immutable child versions carry channel/category/content/parameter schema. Provider artifacts map versions to delivery objects and provider-owned approval. Once a version leaves DRAFT, content cannot be edited. Create a new version and activate it only after provider readiness; the previous active version remains available while approval is pending. Queued deliveries retain their chosen version.

The dashboard supports HTML paste and .html upload, declared variables, sanitized desktop/mobile iframe preview, plain-text preview, linked asset listing and allowlisted test sends. The compiler rejects scripts, forms, handlers, unsafe/insecure URLs, embedded media and unresolved variables, then sanitizes allowed email markup. Variables are escaped server-side. Images/asset URLs must be public HTTPS. `communication_assets` stores references/metadata, not binaries. There is no storage uploader in V1: provision assets externally and paste their public URLs. Video uses a clickable poster link; HTML5 video is rejected.

Delivery resolves `name`, `message_title`, `message_body` and declared server event fields (`order_id`, `order_number`, `total_paise`, `discount_paise`, `payment_status`, `shipment_status`, `subscription_status`, `interval_days`, `next_charge_at`, `event_at`). Order content may use one indexed, customer-owned order lookup; it is never an audience scan. Campaign constants cannot override these authoritative values. Scheduled campaigns without a correlated order cannot invent order variables. Monetary variables are integer paise. Other declared values are campaign constants configured in the rule editor. OTP uses its separate challenge resolver.

Brevo defaults to direct rendered htmlContent, with an optional provider-template ID. Uppermost HTML does not require provider approval or repeated Brevo synchronization. Set and verify the sender domain and COMMUNICATION_EMAIL_FROM before testing.

Meta WhatsApp uses version-specific template names/languages and API submission or signed status events. Admins cannot mark an artifact approved. Production sends require APPROVED; rejection/disabling blocks sends without replacing the existing active canonical version. The form supports body templates and Meta authentication copy-code format. Advanced media/header/button templates require canonical structured_content via the validated admin API and corresponding send-component support; they are not a complete visual builder. The API refresh action conservatively compares draft provider content and can report PROVIDER_CONTENT_MISMATCH for provider-normalized components; use signed provider events or reconcile the exact mapping, never fabricate approval.

SMS readiness requires DLT entity/header/template IDs and approved DLT status, plus ready MSG91 template mapping. Telecom DLT approval is external; MSG91 is delivery/mapping, not its approval authority. Invalid/incomplete mapping blocks sends. A valid DLT entry is an operator-maintained mapping backed by external evidence.

Lemlist is MARKETING/nurture only. It maps a canonical version to a campaign/sequence/step. Every version needs a **distinct campaign**, enforced by a unique partial index, because enrollment executes the provider campaign rather than an isolated frozen step. Syncing a draft into an active version's campaign is rejected. Running campaigns must be explicitly paused before sync. Declared personalization placeholders survive sanitization; unknown variables fail compilation. Freeze the mapped provider sequence after sync; external edits can still invalidate canonical parity.

`COMMUNICATION_PROVIDER_MUTATIONS_ENABLED=false` disables Meta submission and Lemlist synchronization until an operator deliberately enables them. Nothing was submitted or synchronized during implementation. Brevo and Meta callbacks use their existing/signed security boundaries. `/api/communications/webhooks/msg91` and `/lemlist` accept native callbacks as well as the normalized compatibility contract; persistence outages return 503 for provider retry. No raw contact payload or shared secret is stored in the callback ledger.

Configure MSG91's [documented callback headers/fields](https://msg91.com/help/webhook-new/how-to-receive-sms-delivery-reports-via-webhook-new) manually: Authorization Bearer MSG91_COMMUNICATION_WEBHOOK_TOKEN, requestId, numeric status, and an ISO timestamp with timezone in deliveryTime or ts. Local timestamps without an offset are rejected. Native status codes map to sent/delivered/permanent failure.

Create Lemlist's webhook manually with `secret` equal to LEMLIST_COMMUNICATION_WEBHOOK_TOKEN and the deployed `/api/communications/webhooks/lemlist` target. Its [official contract](https://developer.lemlist.com/api-reference/endpoints/webhooks/add-webhook) echoes this secret in the body. Email events correlate leadId/campaignId/stable stepId to the immutable artifact; activity IDs deduplicate callbacks. Early callbacks retain correlation for replay at send acceptance. Unrelated or legacy uncorrelatable activities are acknowledged without attribution. Unsubscribe events use deterministic normalized email suppression. Account fixtures and shared-secret rotation need staging validation; nothing was configured live.

Test sends reuse customer_messages/message_deliveries with a constrained test subject, do not create commerce customers, and always enforce destination allowlists. A provider timeout remains ambiguous even for a test; inspect provider records before retrying.
