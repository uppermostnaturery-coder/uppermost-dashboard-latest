## Razorpay activation invariant

Initial recurring activation requires both a strictly validated captured `RECURRING_AUTH` payment and the exactly correlated recurring mandate in `ACTIVE` with a bound provider token. Mandate confirmation can arrive in a standalone `token.confirmed` event or as an embedded token with `recurring = true` and `recurring_details.status = confirmed` in a signed capture/verified provider fetch. A token ID alone never activates. Arrival order and duplicate delivery must converge without moving billing dates twice or creating duplicate cycles.

Metric definitions:

- Today / 7D / 30D / 90D use IST calendar boundaries through snapshot time; 48H is rolling. Cards and graph buckets share that window.
- Visitors are distinct recorded visitor IDs. New means first seen within the window; returning means first seen earlier. Missing first-seen history stays unclassified. Recorded sessions are distinct session IDs in the window's events.
- Paired different-source records with the same visitor, path, event and button label within one second are merged as a reporting heuristic; genuine repeats from one source survive. A paired page/product event is one product-view action, and paired generic/Buy events for one button are one intent action. Raw event rows are unchanged. Historical tracking gaps cannot be repaired by queries.
- Order intent includes observed Pre-order/Buy/add-to-order/cart buttons and excludes Buy once, subscription mode choices and Remove. Payment-intent clicks are not completed payments.
- Prepared checkouts count unique server checkout sessions by creation time. Confirmed sales count unique `CONFIRMED` orders with `paid_at` in range, including renewals. Paid revenue is integer paise; aggregate initial/renewal counts remain separate in the response. These totals are intentionally independent of browser attribution.
- Both funnel views show distinct visitors progressing chronologically through activity → product view → order intent → payment intent → experience journey within the selected window. Percentages share one visitor denominator. A journey URL is not proof of a rendered page or a purchase; absent tracking yields incomplete observed journeys.
- Device/browser/OS/source distributions count recorded sessions associated with the selected activity, not raw hits. Referrers use hostnames only. Page groups strip query strings and hashes. Live counters use a three-minute activity window and each active session's latest page, even if its page view predates that window.

### Collection and data contracts

1. Wrap each supported backend route handler with one shared observer. Generate a server-controlled request ID, measure handler duration and record exactly one request completion with method, static normalized route label, status, duration, UTC timestamp, production environment and deployment/release. Preserve original response body/status/CORS; expose the opaque request ID only if compatible. Avoid adding browser headers that would unexpectedly trigger CORS preflights. Classify OPTIONS separately; omit observability ingestion/read endpoints from workload totals to avoid self-logging loops. Route/method inventory is derived from actual exports; unknown platform paths remain a separate bucket rather than unbounded labels.
2. Record safe application outcomes explicitly: success, validation, rejected request, rate limit, business failure, unexpected exception, timeout and dependency failure. Do not assume every 4xx is a defect or every 2xx is a business success. Zod diagnostics contain only allowlisted field names and issue codes. Do not parse arbitrary response bodies, provider errors or console messages into persistent telemetry. Add optional dependency spans at existing provider-client boundaries without changing retries or business decisions.
3. Use Vercel's supported post-response lifecycle for bounded persistence; a floating fetch/promise is not reliable on serverless. Telemetry failure cannot replace the original result or block payment. Data write timeouts, ingestion-failure counters/logs and missing-data presentation are required. This is best-effort app instrumentation, not a guarantee that a terminated process records its own failure.
4. Ingest Vercel production Drains through a verified server endpoint only after checking the actual team's plan, source schema and signing procedure. Verify authenticity against the raw bytes, enforce payload/batch limits, deduplicate provider log IDs and reject other projects/environments. Never persist the raw log envelope. Extract allowlisted platform failure categories and request/deployment correlation. Platform errors and app completions remain separate datasets unless matching identifiers establish reconciliation; they must never inflate the API request denominator. The documented log schema does not guarantee handler duration, so latency comes from measured request completions, not invented drain fields.
5. Store sanitized request observations in a new service-only RLS table with unique event IDs and timestamp/route indexes. Retain observations for 30 days initially; use indexed server-side SQL aggregation and bounded queries for overview/route charts. Start with 1h/24h/7d/30d windows, with explicit retained coverage boundaries. p50/p95/p99 use observed durations and disclose sample counts. Any future rollup percentiles must use mergeable distributions, not averages of percentiles. Add a separately authorized retention operation; an endpoint must never silently delete commerce or customer data.
6. Initialize Sentry once in Next.js and once site-wide in the Framer storefront. Use a pinned supported SDK and release/environment tags. Capture unhandled exceptions, rejected promises and explicitly instrumented API failures. Persistent frontend logs are allowlisted structured events (component, normalized endpoint, status/error code, duration and request ID), not arbitrary console copies. Include handled checkout/navigation failures where the UI catches errors. Browser events are diagnostic evidence, never authoritative payment evidence. Sentry errors/logs have plan-dependent retention and quota; they are not permanent archives.
7. Default privacy: sendDefaultPii false; no user identity binding, session replay, console capture, DOM/form content, request/response bodies, cookies, auth headers or query values. Sanitize event, breadcrumb, span and log hooks separately, including experience tokens in URLs and exception strings. Drop unsafe free text rather than trusting regex alone. Do not send database service keys, Razorpay signatures, customer/guest/checkout secrets, full contact details or addresses. Browser tracing starts with a low explicit sample rate; do not send trace headers to Razorpay or other unapproved domains. Sampling is always displayed separately from complete request metrics.

All 23 current backend route files are wrapped. An immutable response and unread request body are preserved; alias calls share AsyncLocalStorage so one incoming request produces one completion. Each completion gets a server-generated request ID, also allowed in private Sentry tags. Backend 5xx results and exceptions generate safe diagnostics. `commerceJson` marks explicit unsuccessful 2xx outcomes; Zod failures are classified as validation. No arbitrary response/provider body is inspected. Handler duration excludes network, cold-start/platform scheduling and streamed response-body transfer. Current implementation does not separately time every external dependency or detect paid-but-unconfirmed delays from order reconciliation; those require additional targeted instrumentation. It does not claim end-to-end distributed tracing.

The Vercel lifecycle uses waitUntil with a two-second database write deadline and bounded Sentry flush. Metrics storage failures cannot replace an API response; one private Sentry storage warning per minute per instance provides independent failure evidence when possible. Process termination before instrumentation, unavailable network, blocked browser SDKs or simultaneous provider outages can still lose telemetry. Receiving observations is not an uptime guarantee; quiet/stale coverage is explicitly unknown. There is no independent heartbeat or external uptime monitor in this release.

Migration `20261021003205_production_observability.sql` creates only observability_events and the server-only aggregate RPC. RLS is enabled with no public policies. PUBLIC/anon/authenticated have no table or RPC access; service_role has SELECT/INSERT/DELETE, not UPDATE. Duplicate platform IDs use ON CONFLICT DO NOTHING.
